# 에이전트 공통 지침

## 개발 방법론
- CBD(Component-Based Development) 방법론으로 개발하라: `cbd` 스킬
- 새 기능, 새 장치, 새 외부 연동은 컴포넌트 명세를 먼저 쓰고 구현하라
- 컴포넌트는 인터페이스로만 연결하고, 조립은 조립 루트 한 곳에서만 하라

## 설계 원칙
- P1. 컴포넌트 코드는 하나의 루프 스레드에서만 실행하라
- P2. 블로킹 호출은 전용 스레드에서만 하라
- P3. 외부에서 온 길이와 인덱스를 믿지 마라
- P4. 실패에는 응답하고, 버림은 기록하라
- P5. 모든 큐에 상한을 두어라

## 스킬 적용
- C++ 작업에는 `cpp` 스킬을 적용하라
- 스레드, 큐, 프로토콜, 연결 복구, 안전, 설정, 로그, 설계 문서에는 `architecture` 스킬을 적용하라
- 컴포넌트 추가, 분리, 조립에는 `cbd` 스킬을 적용하라
- 시험 작성에는 `testing` 스킬을 적용하라
- CMake 작업에는 `cmake` 스킬을 적용하라
- 기존 코드가 규약과 다르면 작업 범위 밖의 코드는 고치지 말고 차이를 보고하라

## 판단과 질문
- 추측으로 값을 만들지 마라. 다음은 사용자에게 묻고, 답을 받기 전에는 구현하지 마라
  - 안전 임계값, 정지 조건, 타임아웃, 재시도 횟수
  - 프로토콜 값: 옵코드, 필드 단위와 배율, 바이트 순서, 체크섬 방식, 주소
  - 외부 인터페이스와 화면 메시지 형식, 설정 키의 추가, 변경, 삭제
  - 시간 계약(주기, 마감, 처리량)과 큐 상한
  - P1–P5와 규약의 예외
  - 요구가 서로 충돌하거나 두 가지 이상으로 해석되는 경우
- 다음은 스스로 정하고 결과 보고에 밝혀라: 내부 이름, 파일 배치, 리팩터링, 시험 구성
- 질문할 때는 선택지와 각 선택의 결과, 권장안을 함께 제시하라
- 답을 받을 수 없는 실행이면 그 부분을 구현하지 말고, 가정과 함께 설계 문서의 현장 확인 항목이나 미구현 항목에 기록하라
- 명세에서 가져온 값에는 출처(문서와 절, 사용자 답변, 측정)를 주석이나 설계 문서에 남겨라. 출처 없는 값을 명세 값처럼 쓰지 마라
- 결과 보고에는 한 것, 검증한 것, 검증하지 못한 것, 세운 가정을 구분해서 적어라

## 문서 지침
- 영문 용어 뒤에 한국어 조사나 접미사를 직접 붙이지 마라
- 코드 블록과 코드 주석에는 영어만 사용하라
- 설계를 바꾸면 설계 문서의 해당 표(컴포넌트, 큐, 감지와 복구, 현장 확인, 미구현)를 함께 갱신하라

## 형상 지침
- 다음 형식의 커밋 메시지를 사용하라: `add: ...`, `fix: ...`, `refactor: ...`, `docs: ...`, `test: ...`
- 영문 소문자로 작성하라
- 외부 형식, 설정 키, 공개 인터페이스의 호환을 깨는 커밋은 형식 뒤에 `!`를 붙여라: `refactor!: rename vms config keys`
- 논리적 단위로 분할하여 커밋하라
