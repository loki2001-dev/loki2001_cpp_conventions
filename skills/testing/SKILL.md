# 시험 전략

## 수준

| 수준 | 대상 | 도구 |
| --- | --- | --- |
| 단위 | 코덱 경계, 상태 기계 전이, 범위 검사, 큐 넘침, 설정 파싱 | Catch2. 실행 파일에 포함하지 않는다 |
| 퍼징 | 코덱, 프레임 조립, 설정과 화면 메시지 파서 | libFuzzer(Clang) + ASan + UBSan |
| 가상 통합 | 실제 실행 파일 하나 + 가짜 상대 장치 전부 | `simulation/`의 스크립트 |
| 현장 | 가상 시험이 다룰 수 없는 것 | 설계 문서의 현장 확인 항목 |

## 단위 시험

- 코덱마다 짧은 프레임, 길이 상한 초과, 깨진 체크섬, 동기 바이트 앞의 쓰레기 바이트를 시험하라
- 상태 기계는 모든 정지 이유와 거절 이유가 나오는 경로를 시험하라
- 범위 검사는 경계값(최소, 최대, 최소−1, 최대+1)을 시험하라
- 큐는 상한에서의 넘침 정책과 누적 버림 수를 시험하라
- 시험 파일은 `tests/{ClassName}Test.cpp`로 두고, 시험 이름은 `"{ClassName} {behaviour}"`로 적어라

```cpp
TEST_CASE("FrameReader rejects a read past the end") {
    const uint8_t bytes[] = {0x01};
    FrameReader reader(ByteView(bytes, sizeof(bytes)));
    uint16_t value = 0;
    REQUIRE_FALSE(reader.readU16Be(value));
}
```

- 스레드 경계를 넘는 클래스(`UvLoop::post()`, `BlockingWorker`, `StateSlot`, 락을 쓰는 큐)는 여러 스레드가 동시에 반복 호출하는 스트레스 시험을 두고 `thread` 빌드에서 실행하라

## 퍼징

- 외부에서 바이트를 받는 모든 함수를 퍼즈 대상으로 만들어라: 코덱 해석, `FrameReader`, 스트림 프레임 조립기, 설정 파서, 화면 메시지 해석
- 대상마다 `tests/fuzz/{ClassName}Fuzz.cpp`에 `LLVMFuzzerTestOneInput` 하나를 둬라 (`cmake` 스킬의 퍼징)
- 퍼즈 대상은 결정적이어야 한다. 시각, 난수, 소켓, 파일, 전역 상태를 쓰지 말고, 로그는 오류 수준만 남겨라
- 스트림 조립기는 입력을 여러 조각으로 나눠 넣어 조각 경계에서의 재동기를 시험하라
- 시드 코퍼스로 명세의 예시 프레임과 현장에서 캡처한 프레임을 `tests/fuzz/corpus/{target}/`에 커밋하라
- 퍼징으로 찾은 크래시 입력은 단위 시험으로 옮겨 회귀 시험으로 남기고, 코퍼스에도 추가하라
- CI에서는 대상마다 60초씩 돌리고, 더 긴 실행(예: 1시간)은 야간 작업으로 돌려라

```cpp
#include <cstddef>
#include <cstdint>

#include "codec/PerceptionCodec.h"
#include "model/ByteView.h"

extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    PerceptionCodec codec;
    perception_header header{};
    codec.parseHeader(ByteView(data, size), header);
    return 0;
}
```

## 가상 통합 시험

- 실제 프로세스는 시험 대상 하나뿐이고, 상대 장치는 모두 가짜로 띄워라
- 판정은 로그가 아니라 가짜 장치와 화면이 실제로 받은 것으로 하라. "보냈다"는 로그는 선로에 도달했다는 증거가 아니다
- 가짜 장치는 실제 장치만큼 엄격하게 만들어라. 등록 없이 상태를 보내는 가짜 장치는 등록 누락 결함을 숨긴다
- 가짜 장치의 엄격함(등록 요구, CRC 검증, 형식 검사)을 명세 문서의 요구와 대조하라
- 시험 설정은 실행 시점에만 덮어써라. 커밋된 설정 파일은 차량 설정과 같아야 한다
- 시리얼 장치는 TCP 브리지(`tcp:host:port`)로 대체해서 시험하되, 기본 실행에서는 제외하라

## 시나리오 목록

| 시나리오 | 확인하는 것 |
| --- | --- |
| 기본 순환 | 모든 명령 경로와 상태 경로 |
| 선택 장치 부재 | 대체 동작(예: 기준 위치 사용) |
| 시리얼 브리지 | 과전류 정지, 시리얼 프레이밍과 주소 지정 |
| 규격 속도 부하 | 규격이 정한 속도에서 메시지를 하나도 잃지 않음 |
| 과부하(예: 규격의 96배) | 성능이 떨어져도 멈추지 않고 회복함 |
| 느린 상대, 응답 없는 상대 | 차량 제어에 영향이 없음 |
| 주소에 도달할 수 없는 상대 | 같음. 통신망 단절 조건 |
| 허용되지 않은 상대의 명령 | 거절, 이유와 상대 주소 기록, 기구가 움직이지 않음 |
| 잘못된 인증서의 TLS 상대 | 연결 거부와 기록 |
| 깨진 프레임 섞기 | 동기 재획득, 무수신 감지, 세션 복구 |
| 시작과 정지 반복(예: 100회) | 정지 경로의 교착, 이중 해제, 스레드와 자식 프로세스 누수 |
| 연결 중, 요청 처리 중 정지 | 전용 스레드 조인과 늦게 도착한 콜백의 안전한 처리 |
| 자식 프로세스 비정상 종료 | 회수와 기록, 좀비 없음 |

## 판정 기준

- 모든 시험(단위, 가상 통합, 부하, 장애 주입)에서 다음 중 하나라도 나오면 결함이다
  - 비정상 종료: crash, `SIGSEGV`, `SIGABRT`, `std::terminate`
  - 교착: 제한 시간 안에 끝나지 않는 시험, 끝나지 않는 정지
  - 좀비: 정지 뒤 `<defunct>` 상태로 남은 자식 프로세스
  - 새니타이저 보고: ASan, UBSan, TSan이 보고한 오류 한 건
- 모든 시험에 제한 시간을 두어라. 넘기면 모든 스레드의 스택을 남기고(`gdb -batch -ex "thread apply all bt" -p <pid>`) 실패로 판정하라
- 단위 시험은 `address` 빌드와 `thread` 빌드에서 각각 통과해야 한다 (`cmake` 스킬의 새니타이저)
- 가상 통합 시험과 장애 주입 시험은 새니타이저 빌드로도 한 번씩 실행하라. 속도와 지연 판정은 `Release` 빌드에서만 하라
- 시간 계약(마감, 핸들러 예산, 지터 허용치, 처리량)을 넘으면 결함이다. 측정 최악값은 조건과 함께 설계 문서의 시간 계약 표에 남겨라
- 계약 안이라도 측정 최악값이 이전 기록보다 나빠졌으면 원인을 찾아 설계 기록에 남겨라
- 규격 속도에서 메시지를 잃으면 결함이다
- 과부하에서 메시지를 잃는 것은 상한 있는 큐가 제 역할을 한 것이다. 대신 멈추지 않고 회복해야 하며 버림이 기록되어야 한다
- 두 판정 기준이 다르므로 부하 시험은 두 수준으로 따로 둬라
- 느린 상대 시험은 제어 주기 간격의 최악값과 화면 명령 왕복 시간의 최악값을 측정해 판정하라

## 애플리케이션 안의 시험 도우미

- 실행 파일 안에 두는 시험 도우미 함수는 `TDD_` 접두사를 붙여라: `TDD_waitForTcpConnection()`
- 시험 도우미는 클래스 안에서 `// test helper`, `// test execution` 섹션에 모아라

## 현장 확인 항목

가상 시험으로 확인할 수 없는 것은 설계 문서의 현장 확인 항목에 확인 방법과 함께 적어라.

- 포트 번호, 통신 속도, 패리티, 배선
- 명세가 불확실한 옵코드와 단위
- 실측이 필요한 임계값
- 실제 장치와의 등록, 수신
