# CBD 방법론

시스템은 독립적으로 명세하고, 구현하고, 교체하고, 시험할 수 있는 컴포넌트를 조립해서 만든다. 컴포넌트는 인터페이스로만 서로를 알고, 조립은 한 곳에서만 한다.

## 개념과 구현의 대응

| CBD 개념 | 이 규약에서의 구현 |
| --- | --- |
| 컴포넌트 | `IComponent`를 구현한 클래스 하나. `src/component/`에 둔다 |
| 컴포넌트 계약 | `initialize()`, `start()`, `stop()` 생명주기와 루프 스레드 실행 규칙 |
| 제공 인터페이스 | 버스에 발행하는 메시지 타입, 쓰기 권한을 가진 상태 종류(`I{Kind}StatusWriter`) |
| 요구 인터페이스 | 구독하는 메시지 타입, `IStateReader`, 전송 계층 인터페이스, 설정 구조체 |
| 커넥터 | `MessageBus`(이벤트, 명령), `StateStore`(상태), `UvLoop::post()`(스레드 경계) |
| 조립 | `Application`. 구체 컴포넌트 타입을 아는 유일한 곳 |
| 공통 골격 | 여러 컴포넌트가 공유하는 처리는 기반 클래스 하나에 두고 차이만 재정의한다 |

## 개발 절차

각 단계의 산출물이 있어야 다음 단계로 넘어간다. 작은 변경이면 해당 단계의 산출물만 갱신하라.

1. **요구 분석**: 외부 장치와 사용자 명령을 나열하고, 장치별 주소, 프로토콜, 주기, 방향을 표로 정리한다
2. **컴포넌트 식별**: 책임 하나에 컴포넌트 하나를 둔다. 기존 프로그램을 옮길 때는 기존 프로세스 하나를 컴포넌트 하나로 옮기는 것을 출발점으로 삼는다. 여러 컴포넌트에 같은 처리가 복사되어 있으면 공통 골격으로 묶는다
3. **상호작용 설계**: 명령 경로와 상태 경로를 흐름도로 그린다. 어떤 메시지를 누가 발행하고 누가 구독하는지, 어떤 상태를 누가 쓰는지 정한다
4. **컴포넌트 명세**: `references/component-spec-template.md` 양식으로 컴포넌트마다 명세를 작성한다
5. **구현**: 명세에 적힌 제공, 요구 인터페이스만 사용해서 구현한다. 명세에 없는 의존이 필요하면 명세부터 고친다
6. **조립**: `Application`에 등록하고, 조립 시점 검증(배선 충돌, 필수 설정)을 추가한다
7. **시험**: 컴포넌트 단위 시험과 가상 통합 시험을 작성한다 (`testing` 스킬)
8. **기록**: 설계 결정과 근거, 미구현 항목, 현장 확인 항목을 설계 문서에 남긴다 (`architecture` 스킬의 설계 기록)

## 컴포넌트 규칙

- 컴포넌트는 다른 컴포넌트를 직접 참조하지 마라. 다른 컴포넌트의 헤더도 include하지 마라
- 컴포넌트 사이의 통신은 `MessageBus`의 메시지와 `StateStore`의 상태로만 하라
- 발행자는 구독자를 알지 못하게 하라. 소비자를 추가해도 발행자 코드는 바뀌지 않아야 한다
- 컴포넌트는 자기 상태 종류만 써라. 쓰기 권한은 상태 종류별 쓰기 인터페이스로 생성자에서 받아라
- 읽기는 누구나 할 수 있지만 `IStateReader`의 불변 스냅숏으로만 하라
- 모든 의존은 생성자로 주입하라. 싱글턴, 전역 객체, 서비스 탐색을 사용하지 마라
- 생성자 매개변수 목록이 그 컴포넌트의 요구 인터페이스 목록과 일치해야 한다
- 컴포넌트 코드는 루프 스레드에서만 실행하라. 블로킹 호출은 전송 계층의 전용 스레드로 넘겨라
- 한 컴포넌트의 실패가 다른 컴포넌트를 멈추지 않게 하라. `initialize()`나 `start()`가 실패하면 기록하고 그 컴포넌트만 제외하라
- 컴포넌트는 가짜 커넥터와 가짜 전송 계층으로 단독 시험할 수 있어야 한다

## 조립 규칙

- 구체 컴포넌트 타입은 `Application`(조립 루트)에서만 생성하라
- 등록 순서를 의존 순서로 삼고, `stop()`은 역순으로 호출하라
- 조립 시점에 검증할 수 있는 것은 모두 검증하라. 사람이 다칠 수 있는 설정 충돌(릴레이 채널 중복 등)이 있으면 실행을 거부하라
- 조립 결과(시작된 컴포넌트 수, 제외된 컴포넌트와 이유)를 시작 로그에 남겨라

## 컴포넌트 추가 점검표

- [ ] 명세를 작성했다: 책임, 주기, 제공 인터페이스, 요구 인터페이스, 스레드, 실패 감지와 복구, 큐 상한, 로그 태그, 설정 키
- [ ] 다른 컴포넌트를 include하지 않는다
- [ ] 새 메시지와 상태는 `src/model/`의 값 타입으로 정의했다
- [ ] 새 상태 종류에는 전용 쓰기 인터페이스를 추가했다
- [ ] 블로킹 호출이 루프 스레드에 없다
- [ ] 모든 큐에 상한과 넘침 정책이 있다
- [ ] 시간 계약(주기, 마감, 핸들러 예산, 처리량)을 출처와 함께 명세에 적고 측정했다
- [ ] 거절과 실패에는 이유가 담긴 응답이나 로그가 있다
- [ ] `Application`에 의존 순서대로 등록했다
- [ ] 단위 시험과 가상 통합 시험을 추가했다
- [ ] 설계 문서의 컴포넌트 목록과 흐름도를 갱신했다
