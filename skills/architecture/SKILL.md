# 아키텍처 규칙

## 설계 원칙

모든 설계 판단은 다섯 원칙으로 설명할 수 있어야 한다. 원칙을 어기는 변경은 설계 문서에 근거를 남긴 뒤에만 하라.

| 원칙 | 규칙 |
| --- | --- |
| P1. 하나의 루프 | 컴포넌트 코드는 하나의 스레드(루프 스레드)에서만 실행한다 |
| P2. 블로킹은 밖으로 | 블로킹 호출은 전용 스레드에서만 한다 |
| P3. 경계 검사 | 외부에서 온 길이와 인덱스는 믿지 않는다 |
| P4. 조용히 실패하지 않기 | 실패에는 응답하고, 버림은 기록한다 |
| P5. 유한한 자원 | 모든 큐에는 상한이 있다 |

## 계층

위에서 아래로만 의존하라. 아래 계층은 위 계층을 include하지 마라.

| 계층 | 디렉터리 | 내용 |
| --- | --- | --- |
| app | `src/app` | 조립, 시작 순서, 정지 순서, 배선 검증, `main` |
| component | `src/component` | 컴포넌트. 장치 프로토콜 해석과 상태 기록 (`cbd` 스킬) |
| control | `src/control` | 기구 상태 기계, 배선표 |
| core | `src/core` | `MessageBus`, `StateStore`, `UvLoop`, `UvTimer`, `IComponent` |
| codec | `src/codec` | 프레임 조립과 해석. 프로토콜 하나에 코덱 하나 |
| network | `src/network` | TCP, 시리얼, WebSocket, HTTPS, MQTT. 블로킹은 여기서 스레드로 격리 |
| model | `src/model` | 값 타입. 메시지, 상태, `ByteView` |
| config | `src/config` | 설정 파서, 타입 있는 설정 구조체 |
| util | `src/util` | 로거, 좌표 계산, JSON, 시각 |

## 스레드 (P1, P2)

- 컴포넌트, 버스, 타이머, 비블로킹 소켓은 모두 루프 스레드에서 실행하라
- 루프 스레드를 붙잡는 호출을 하지 마라: 동기 연결, 동기 발행, 블로킹 읽기, `sleep`, 긴 계산
- 블로킹 호출은 전송 계층의 전용 스레드에서 실행하라. 다음은 전용 스레드 대상이다
  - libuv가 다루지 못하는 장치(Windows COM 포트)
  - 동기 API(paho MQTT 연결, 발행)
  - 수 초가 걸리는 요청(HTTPS 추론 요청)
  - 자체 서비스 루프를 가진 라이브러리(libwebsockets)
- 전용 스레드의 결과는 `UvLoop::post()`로만 루프에 돌려줘라. 다른 공유 경로를 만들지 마라
- 차량 밖 상대(관제센터 등)는 현장에서 가장 먼저 끊긴다고 가정하라. 그 호출이 루프에 있으면 제어가 함께 멈춘다
- 루프 지연은 성능 문제가 아니라 안전 문제로 다뤄라. 폴링이 멈추면 리밋 스위치와 과전류 판정도 멈춘다

## 메시지와 상태

- 하나의 이벤트가 여러 곳에 필요하면 `MessageBus`에 발행하라. 발행자는 구독자를 모른다
- 메시지는 값 타입으로 정의하고 값 전체만 옮겨라. 바이트 복사로 구조체 일부를 옮기지 마라
- 공유 상태는 `StateStore` 한 곳에 둬라. 상태 종류마다 `StateSlot<T>` 하나를 둔다
- 쓰기는 상태 종류별 쓰기 인터페이스로 자기 상태만, 읽기는 `std::shared_ptr<const T>` 스냅숏으로 하라
- 스냅숏을 들고 있는 동안 값이 바뀌지 않음을 전제로 코드를 작성하라

## 큐 (P5)

- 모든 큐에 상한과 넘침 정책을 정하라. 상한 없는 `std::queue`, `std::deque`를 큐로 쓰지 마라
- 넘침 정책은 데이터의 성격으로 정하라
  - 최신 상태가 중요한 발행: 가장 오래된 것을 버림
  - 명령, 요청: 거절하고 호출자에게 실패로 알림
- 버릴 때마다 누적 버림 수를 로그에 남겨라. 현장에서 "명령이 사라진다"를 로그만으로 추적할 수 있어야 한다
- 설계 문서에 큐 목록(이름, 상한, 넘침 정책)을 표로 유지하라

## 프레임과 값 검사 (P3)

- 바이트 버퍼는 `ByteView`(포인터와 길이)로 넘겨라. 포인터만 넘기지 마라
- 프레임 해석은 `FrameReader`로 하라. 읽기 전에 남은 길이를 확인하고, 모자라면 프레임을 버려라
- 고정 오프셋으로 직접 읽지 마라
- 코덱마다 길이 상한을 두어라. 상한을 넘으면 프레임을 버리고 동기 바이트부터 다시 찾아라
- 부호 없는 뺄셈으로 길이를 계산하기 전에 피감수가 충분한지 확인하라
- 체크섬과 CRC가 있는 프로토콜은 수신 시 반드시 검증하라
- 선언된 개수를 믿지 말고 실제로 읽은 만큼만 저장하라
- 외부에서 온 인덱스, 번호, 각도는 받는 지점에서 범위를 검사하고, 벗어나면 거절하고 기록하라
- 배열 크기와 허용 범위는 같은 상수를 공유하고 `static_assert`로 묶어라
- 바이트로 좁히는 변환 전에는 범위를 검사하라

## 연결과 복구

- 모든 외부 호출에 타임아웃을 두어라. 타임아웃이 지나면 링크가 죽은 것으로 보고 끊은 뒤 다시 연결하라
- 상대마다 감지 방법과 복구 방법을 정하고 설계 문서에 표로 남겨라
  - 연결 끊김: 일정 간격 후 재접속, 그 사이 상태는 오프라인으로 표시
  - N초 무수신: 세션을 끊고 다시 대기
  - 확인 응답 없음: 링크를 죽은 것으로 보고 재접속
  - 재접속 후 등록이 필요한 상대: 대상별로 다시 등록
- 무수신 타이머는 원시 바이트 수신이 아니라 완성된 프레임 수신 시점에 초기화하라. 길이가 깨진 프레임이 들어오면 바이트는 계속 오지만 프레임은 완성되지 않으므로, 바이트 기준 초기화는 멈춤을 영원히 감지하지 못한다
- 세션을 끊을 때는 조립 버퍼도 비워라
- 재시도하지 않는 연결은 알려진 제약으로 설계 문서에 기록하라

## 안전

- 사람이 다칠 수 있는 기구는 상태 기계(`idle`, `running`, 정지 상태들)로 구동하라
- 구동 중에는 정지 조건(리밋, 과전류, 최대 구동 시간, 정지 명령)을 제어 주기마다 검사하라
- 시작 거절과 정지에는 반드시 이유를 붙이고 화면까지 전달하라: `rejected_emergency`, `rejected_manual`, `rejected_invalid`, `stopped_limit`, `stopped_current`, `stopped_timeout`, `stopped_command`
- 비상 정지 같은 전역 스위치는 에지에서 한 번만 처리하라. 매 주기 보내면 링크가 막힌다
- 정해진 시간만 켜야 하는 출력은 소프트웨어 타이머가 아니라 장치의 하드웨어 타이머(예: Modbus Flash-ON)로 구동하라. 프로세스가 죽어도 출력이 풀려야 한다
- 시작 시 배선표를 검증하고, 채널 충돌(두 기구가 같은 채널, 한 기구의 열기와 닫기가 같은 채널)이 있으면 실행을 거부하라
- 안전 임계값에는 하한과 그 이유를 설정 문서에 남겨라

## 설정

- 설정은 타입 있는 구조체로 묶어라. 키 하나는 의미 하나만 가진다
- 현장 값(주소, 좌표, 임계값)을 소스에 하드코딩하지 마라
- 없는 값과 범위를 벗어난 값은 기록하고, 대신 쓰는 기본값을 로그에 밝혀라. 조용히 기본값으로 넘어가는 경로를 만들지 마라
- 시작할 때 모든 설정 값을 로그에 요약하라
- 두 값 중 하나만 유효한 설정(예: 0 또는 1)은 그 밖의 값에 경고하라

## 로그

- 로그만으로 현장 원인을 찾을 수 있게 써라
- 형식: `[수준][시각.밀리초][스레드] [장치 태그][분류 태그] 내용`
- 분류 태그: `LIFE`(생명주기), `CFG`(설정), `NET`(연결), `TX`, `RX`, `CMD`(명령), `STAT`(상태), `HW`(하드웨어), `PROT`(프로토콜 오류), `SYS`(자원, 큐), `TEST`
- 내용은 영어 소문자 동사구 뒤에 `key=value`로 값을 붙여라: `rejected reason=manual target=ramp`
- 콘솔과 파일은 같은 형식을 쓰고, 파일에는 BOM을 붙여 한글을 메모장에서 읽을 수 있게 하라
- 파일은 `YYYY-MM-DD-HH.log`로 시간마다 나누고, 보존은 기간 다음 총용량 순으로 오래된 것부터 지워라. 쓰고 있는 파일은 지우지 마라
- 서드파티 라이브러리 로그도 같은 로거로 모아라. 표준 오류로 새게 두지 마라
- "보냈다"는 로그는 전송 성공의 증거가 아니다. 판정이 필요하면 상대가 받은 것으로 확인하라

## 설계 기록

- 설계 결정에는 근거를 남기고, 가능하면 측정값으로 남겨라
- 기존 시스템을 옮길 때는 발견한 결함마다 "문제, 결과, 현재의 답"을 기록하라
- 가상 시험으로 확인할 수 없는 항목은 현장 확인 항목으로, 구현하지 않은 항목은 미구현 항목으로 따로 기록하라
- 양식은 `references/design-record.md`를 따르라
