# 아키텍처 규칙

## 설계 원칙

모든 설계 판단은 다섯 원칙으로 설명할 수 있어야 한다. 원칙을 어기는 변경은 아래 "원칙 예외" 절차를 거친 뒤에만 하라.

| 원칙 | 규칙 |
| --- | --- |
| P1. 하나의 루프 | 컴포넌트 코드는 하나의 스레드(루프 스레드)에서만 실행한다 |
| P2. 블로킹은 밖으로 | 블로킹 호출은 전용 스레드에서만 한다 |
| P3. 경계 검사 | 외부에서 온 길이와 인덱스는 믿지 않는다 |
| P4. 조용히 실패하지 않기 | 실패에는 응답하고, 버림은 기록한다 |
| P5. 유한한 자원 | 모든 큐에는 상한이 있다 |

## 원칙 예외

- 원칙을 지킬 수 없으면 먼저 사용자에게 묻고, 승인받은 예외만 구현하라
- 예외마다 `EX-P{원칙}-{세 자리 번호}` 형식의 ID를 붙여 설계 문서의 원칙 예외 표에 올려라: ID, 원칙, 위치, 이유, 완화책, 승인, 재검토 조건
- 예외를 적용한 코드에는 ID와 이유를 표식으로 남겨라: `// exception: EX-P2-001 vendor sdk has no async connect`
- 표에 없는 ID를 코드에 쓰지 말고, 표식 없는 예외를 만들지 마라. `tools/check-conventions`가 표식과 표를 대조한다 (`cpp` 스킬의 검사)
- 완화책을 반드시 적어라. 예: 루프에서 블로킹 호출을 허용하면 호출에 타임아웃을 두고 최악 시간을 측정해 시간 계약에 반영한다
- 재검토 조건(라이브러리 교체, 날짜, 릴리스)이 오면 예외를 없앨 수 있는지 다시 보고, 없앤 예외는 표에서 지우지 말고 "해제"로 표시하라
- `NOLINT`로 검사를 억제하는 것도 규약 예외다. 검사 이름과 이유를 적어라

## 계층

위에서 아래로만 의존하라. 아래 계층은 위 계층을 include하지 마라.

| 계층 | 디렉터리 | 내용 |
| --- | --- | --- |
| app | `src/app` | 조립, 시작 순서, 정지 순서, 배선 검증, `main` |
| component | `src/component` | 컴포넌트. 장치 프로토콜 해석과 상태 기록 (`cbd` 스킬) |
| control | `src/control` | 기구 상태 기계, 배선표 |
| core | `src/core` | `MessageBus`, `StateStore`, `UvLoop`, `UvTimer`, `IComponent` |
| codec | `src/codec` | 프레임 조립과 해석. 프로토콜 하나에 코덱 하나 |
| network | `src/network` | TCP, 시리얼, WebSocket, HTTPS, MQTT. 블로킹은 여기서 스레드로 격리 |
| model | `src/model` | 값 타입. 메시지, 상태, `ByteView` |
| config | `src/config` | 설정 파서, 타입 있는 설정 구조체 |
| util | `src/util` | 로거, 좌표 계산, JSON, 시각 |

## 스레드 (P1, P2)

- 컴포넌트, 버스, 타이머, 비블로킹 소켓은 모두 루프 스레드에서 실행하라
- 루프 스레드를 붙잡는 호출을 하지 마라: 동기 연결, 동기 발행, 블로킹 읽기, `sleep`, 긴 계산
- 블로킹 호출은 전송 계층의 전용 스레드에서 실행하라. 다음은 전용 스레드 대상이다
  - libuv가 다루지 못하는 장치(Windows COM 포트)
  - 동기 API(paho MQTT 연결, 발행)
  - 수 초가 걸리는 요청(HTTPS 추론 요청)
  - 자체 서비스 루프를 가진 라이브러리(libwebsockets)
- 전용 스레드의 결과는 `UvLoop::post()`로만 루프에 돌려줘라. 다른 공유 경로를 만들지 마라
- 차량 밖 상대(관제센터 등)는 현장에서 가장 먼저 끊긴다고 가정하라. 그 호출이 루프에 있으면 제어가 함께 멈춘다
- 루프 지연은 성능 문제가 아니라 안전 문제로 다뤄라. 폴링이 멈추면 리밋 스위치와 과전류 판정도 멈춘다

## 동기화와 수명

교착(deadlock), 비정상 종료(crash, SIGSEGV), 좀비 프로세스는 한 번이라도 나오면 결함이다.

- 뮤텍스는 루프 스레드와 전용 스레드가 공유하는 자료에만 둬라. 컴포넌트 코드에는 락을 두지 마라 (P1)
- 락은 `std::lock_guard`, `std::unique_lock`, `std::scoped_lock`으로만 잡아라. 뮤텍스의 `lock()`, `unlock()`을 직접 호출하지 마라
- 한 번에 락 하나만 쥐어라. 둘 이상이 꼭 필요하면 `std::scoped_lock`으로 한꺼번에 잡아라
- 락을 쥔 채 콜백, 가상 함수, 블로킹 호출, 다른 객체의 락을 잡는 함수를 호출하지 마라. 필요한 값을 복사하고 락을 푼 뒤에 호출하라
- 조건 변수는 술어를 받는 `wait`만 사용하라. 술어가 읽는 값은 `std::atomic`이어도 같은 뮤텍스를 쥔 채 바꿔라. 그렇지 않으면 깨우기를 잃고 `join()`이 영원히 멈춘다
- `std::thread::detach()`를 사용하지 마라. 스레드는 소유 객체가 멈춤 신호, 깨우기, `join()` 순서로 정리하라
- `join()`은 대상 스레드 밖에서만 호출하라. 전용 스레드가 자기 소유 객체를 파괴하는 경로를 만들지 마라
- 정지는 시작의 역순으로 하라: 전용 스레드 조인, 컴포넌트 `stop()`(등록 역순), 루프 정지, 객체 파괴. 결과를 받을 객체를 전용 스레드 조인 전에 파괴하지 마라
- libuv 핸들의 메모리는 `uv_close` 완료 콜백이 불린 뒤에만 해제하라
- 나중에 실행되는 작업(`post()`, 타이머, libuv 콜백, 버스 구독)은 대상 객체보다 먼저 해제하거나 취소하라

## 프로세스와 비정상 종료

- 외부 프로그램 실행은 꼭 필요할 때만 하라. 실행했으면 반드시 회수하라: `waitpid`로 종료 코드를 받아 기록하고, `popen`은 `pclose`로 닫아라
- 정지할 때 살아 있는 자식 프로세스를 끝내고 회수한 뒤에 종료하라. 좀비와 고아 프로세스를 남기지 마라
- `SIGSEGV`, `SIGABRT`를 잡아서 계속 실행하지 마라. 비정상 종료는 숨기지 말고 코어 덤프(Windows는 미니덤프)를 남겨라
- 재시작은 프로세스 안이 아니라 외부 감시자(systemd `Restart=on-failure`, Windows 서비스 복구 옵션)가 맡게 하라
- 프로세스가 비정상 종료해도 출력이 안전한 상태로 돌아가야 한다 (아래 "안전"의 하드웨어 타이머)

## 메시지와 상태

- 하나의 이벤트가 여러 곳에 필요하면 `MessageBus`에 발행하라. 발행자는 구독자를 모른다
- 메시지는 값 타입으로 정의하고 값 전체만 옮겨라. 바이트 복사로 구조체 일부를 옮기지 마라
- 공유 상태는 `StateStore` 한 곳에 둬라. 상태 종류마다 `StateSlot<T>` 하나를 둔다
- 쓰기는 상태 종류별 쓰기 인터페이스로 자기 상태만, 읽기는 `std::shared_ptr<const T>` 스냅숏으로 하라
- 스냅숏을 들고 있는 동안 값이 바뀌지 않음을 전제로 코드를 작성하라

## 큐 (P5)

- 모든 큐에 상한과 넘침 정책을 정하라. 상한 없는 `std::queue`, `std::deque`를 큐로 쓰지 마라
- 넘침 정책은 데이터의 성격으로 정하라
  - 최신 상태가 중요한 발행: 가장 오래된 것을 버림
  - 명령, 요청: 거절하고 호출자에게 실패로 알림
- 버릴 때마다 누적 버림 수를 로그에 남겨라. 현장에서 "명령이 사라진다"를 로그만으로 추적할 수 있어야 한다
- 설계 문서에 큐 목록(이름, 상한, 넘침 정책)을 표로 유지하라

## 시간 계약

- 주기로 동작하거나 명령에 응답하는 컴포넌트는 명세에 시간 계약을 적어라 (`cbd` 스킬의 명세 양식)
  - 주기와 마감: 주기 시작부터 출력까지 허용되는 시간
  - 핸들러 1회 실행 예산: 루프에서 한 번에 실행되는 콜백의 최대 시간
  - 지터 허용치: 실제 주기 간격이 명목 주기에서 벗어나도 되는 폭
  - 처리량: 규격 속도와 과부하 배수
  - 큐 예산: 상한과 평상시 최대 적재량(고수위)
- 계약 값에는 출처(규격 절, 장치 명세, 측정)를 남겨라. 출처가 없으면 추측하지 말고 질문하라
- 핸들러 예산이 명세에 없으면 가장 짧은 제어 주기의 10%를 기본값으로 삼고, 기본값임을 명세에 밝혀라
- 일반 운영체제(Linux, Windows)에서는 최악 실행 시간(WCET)을 보장할 수 없다. 값은 "측정 최악값"으로 부르고 측정 조건(빌드, 하드웨어, 부하, 측정 시간)을 함께 기록하라
- 루프에 계측을 둬라. 주기 간격과 핸들러 실행 시간의 최악값, 큐 고수위를 주기적으로 `STAT` 로그에 남기고, 예산을 넘을 때마다 `WARN`으로 남겨라: `LOG_WARN(app, sys, "budget exceeded handler=vms_poll elapsed_ms={} budget_ms={}", elapsedMs, budgetMs)`
- 시간 측정에는 `std::chrono::steady_clock`을 사용하라. `system_clock`은 시각 보정으로 뒤로 갈 수 있다
- 설계 문서에 시간 계약 표(컴포넌트, 주기, 마감, 핸들러 예산, 측정 최악값, 측정 조건)를 유지하라

## 프레임과 값 검사 (P3)

- 바이트 버퍼는 `ByteView`(포인터와 길이)로 넘겨라. 포인터만 넘기지 마라
- 프레임 해석은 `FrameReader`로 하라. 읽기 전에 남은 길이를 확인하고, 모자라면 프레임을 버려라
- 고정 오프셋으로 직접 읽지 마라
- 코덱마다 길이 상한을 두어라. 상한을 넘으면 프레임을 버리고 동기 바이트부터 다시 찾아라
- 부호 없는 뺄셈으로 길이를 계산하기 전에 피감수가 충분한지 확인하라
- 체크섬과 CRC가 있는 프로토콜은 수신 시 반드시 검증하라
- 선언된 개수를 믿지 말고 실제로 읽은 만큼만 저장하라
- 외부에서 온 인덱스, 번호, 각도는 받는 지점에서 범위를 검사하고, 벗어나면 거절하고 기록하라
- 배열 크기와 허용 범위는 같은 상수를 공유하고 `static_assert`로 묶어라
- 바이트로 좁히는 변환 전에는 범위를 검사하라

## 연결과 복구

- 모든 외부 호출에 타임아웃을 두어라. 타임아웃이 지나면 링크가 죽은 것으로 보고 끊은 뒤 다시 연결하라
- 상대마다 감지 방법과 복구 방법을 정하고 설계 문서에 표로 남겨라
  - 연결 끊김: 일정 간격 후 재접속, 그 사이 상태는 오프라인으로 표시
  - N초 무수신: 세션을 끊고 다시 대기
  - 확인 응답 없음: 링크를 죽은 것으로 보고 재접속
  - 재접속 후 등록이 필요한 상대: 대상별로 다시 등록
- 무수신 타이머는 원시 바이트 수신이 아니라 완성된 프레임 수신 시점에 초기화하라. 길이가 깨진 프레임이 들어오면 바이트는 계속 오지만 프레임은 완성되지 않으므로, 바이트 기준 초기화는 멈춤을 영원히 감지하지 못한다
- 세션을 끊을 때는 조립 버퍼도 비워라
- 재시도하지 않는 연결은 알려진 제약으로 설계 문서에 기록하라

## 안전

- 사람이 다칠 수 있는 기구는 상태 기계(`idle`, `running`, 정지 상태들)로 구동하라
- 구동 중에는 정지 조건(리밋, 과전류, 최대 구동 시간, 정지 명령)을 제어 주기마다 검사하라
- 시작 거절과 정지에는 반드시 이유를 붙이고 화면까지 전달하라: `rejected_emergency`, `rejected_manual`, `rejected_invalid`, `stopped_limit`, `stopped_current`, `stopped_timeout`, `stopped_command`
- 비상 정지 같은 전역 스위치는 에지에서 한 번만 처리하라. 매 주기 보내면 링크가 막힌다
- 정해진 시간만 켜야 하는 출력은 소프트웨어 타이머가 아니라 장치의 하드웨어 타이머(예: Modbus Flash-ON)로 구동하라. 프로세스가 죽어도 출력이 풀려야 한다
- 시작 시 배선표를 검증하고, 채널 충돌(두 기구가 같은 채널, 한 기구의 열기와 닫기가 같은 채널)이 있으면 실행을 거부하라
- 안전 임계값에는 하한과 그 이유를 설정 문서에 남겨라

## 보안

- 외부에서 온 모든 입력(프레임, 화면 메시지, 설정 파일, 명령)은 P3 경계 검사와 퍼징 대상이다
- 차량 밖 상대(관제센터, 클라우드 추론, 원격 보고)와는 TLS로 통신하고, 인증서와 호스트 이름 검증을 끄지 마라. 시험에서 검증을 꺼야 하면 실행 시점 옵션으로만 끄고 커밋된 설정에는 두지 마라
- 차량 내부 폐쇄망의 평문 프로토콜(Modbus, 시리얼, 장치 전용 TCP)은 알려진 제약으로 설계 문서에 기록하라
- 기구를 움직이는 명령을 받는 입구(화면, 관제)는 허용된 상대만 받아라: 주소 허용 목록이나 인증. 거절은 이유와 상대 주소를 기록하라
- 대기 소켓은 필요한 인터페이스 주소에만 바인드하라. 이유 없이 `0.0.0.0`에 바인드하지 마라
- 비밀 값(비밀번호, 토큰, 키, 인증서 개인 키)을 소스와 커밋된 설정에 두지 마라. 저장소 밖의 파일(소유자만 읽기 권한)이나 환경 변수에서 읽어라
- 비밀 값은 로그, 설정 요약, 오류 메시지에 가려서 남겨라: `password=***`
- 프로세스를 관리자 권한(root, Administrator)으로 실행하지 마라. 장치 접근에 필요한 권한(예: `dialout` 그룹)만 줘라
- 서드파티 라이브러리의 버전과 출처를 설계 문서의 Build 절에 기록하고, 릴리스마다 알려진 취약점(CVE)을 확인하라

## 인터페이스 변경과 버전

- 프로토콜에 버전 필드가 있으면 헤더를 읽는 즉시 검사하고, 모르는 버전의 프레임은 버리고 기록하라. 지원하는 버전 목록은 설계 문서의 프로토콜 절에 남겨라
- 상대가 함께 바뀌지 않는 외부 형식(장치 프로토콜, 화면 메시지, 관제 보고)은 호환을 지켜라
  - 필드는 끝에 추가만 하고, 받는 쪽은 없는 필드에 기본값을 쓰고 모르는 필드는 무시하라
  - 필드 삭제, 의미나 단위 변경은 형식의 버전을 올리고, 옛 버전을 언제까지 받을지 설계 문서에 적어라
- 저장소 안의 메시지 타입과 인터페이스(`I*`)는 호환 계층 없이 한 번에 바꾸되, 구현체, 가짜 장치, 시험을 같은 커밋에서 함께 고쳐라
- 설정 키 이름을 바꾸면 한 릴리스 동안 옛 키도 읽고 경고하라: `LOG_WARN(app, cfg, "deprecated key=old_name use=new_name")`. 다음 릴리스에서 옛 키를 지워라
- 모르는 설정 키는 오타일 수 있으므로 경고하라
- 제품 버전은 `MAJOR.MINOR.PATCH` 하나를 CMake `project(VERSION)`에만 두고 코드는 생성된 헤더로 읽어라 (`cmake` 스킬). 외부 형식이나 설정 키의 호환이 깨지면 `MAJOR`를 올려라
- 시작 로그에 버전, 커밋, 빌드 구성을 남겨라: `LOG_INFO(app, life, "starting version={} commit={} build={}", BUILD_VERSION, BUILD_COMMIT, BUILD_TYPE)`
- 릴리스에는 `vX.Y.Z` git 태그를 붙이고 변경 기록(`CHANGELOG.md`)에 호환이 깨지는 변경을 따로 적어라

## 설정

- 설정은 타입 있는 구조체로 묶어라. 키 하나는 의미 하나만 가진다
- 현장 값(주소, 좌표, 임계값)을 소스에 하드코딩하지 마라
- 없는 값과 범위를 벗어난 값은 기록하고, 대신 쓰는 기본값을 로그에 밝혀라. 조용히 기본값으로 넘어가는 경로를 만들지 마라
- 시작할 때 모든 설정 값을 로그에 요약하라. 비밀 값은 가려라 ("보안")
- 두 값 중 하나만 유효한 설정(예: 0 또는 1)은 그 밖의 값에 경고하라

## 로그

- 로그만으로 현장 원인을 찾을 수 있게 써라
- 형식: `[수준][시각.밀리초][스레드] [장치 태그][분류 태그] 내용`
- 분류 태그: `LIFE`(생명주기), `CFG`(설정), `NET`(연결), `TX`, `RX`, `CMD`(명령), `STAT`(상태), `HW`(하드웨어), `PROT`(프로토콜 오류), `SYS`(자원, 큐), `TEST`
- 내용은 영어 소문자 동사구 뒤에 `key=value`로 값을 붙여라: `rejected reason=manual target=ramp`
- 콘솔과 파일은 같은 형식을 쓰고, 파일에는 BOM을 붙여 한글을 메모장에서 읽을 수 있게 하라
- 파일은 `YYYY-MM-DD-HH.log`로 시간마다 나누고, 보존은 기간 다음 총용량 순으로 오래된 것부터 지워라. 쓰고 있는 파일은 지우지 마라
- 서드파티 라이브러리 로그도 같은 로거로 모아라. 표준 오류로 새게 두지 마라
- "보냈다"는 로그는 전송 성공의 증거가 아니다. 판정이 필요하면 상대가 받은 것으로 확인하라

## 설계 기록

- 설계 결정에는 근거를 남기고, 가능하면 측정값으로 남겨라
- 기존 시스템을 옮길 때는 발견한 결함마다 "문제, 결과, 현재의 답"을 기록하라
- 가상 시험으로 확인할 수 없는 항목은 현장 확인 항목으로, 구현하지 않은 항목은 미구현 항목으로 따로 기록하라
- 양식은 `references/design-record.md`를 따르라
